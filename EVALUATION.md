## Dataset provenance

All training and evaluation data is **synthetic**, generated by `ml_engine.traffic_profiles`. Real public datasets were checked first and found impractical in this environment:

- **MAWI** (https://mawi.wide.ad.jp/mawi/): daily samples are ~1.85GB each and carry no attack ground-truth labels (it's raw, mostly-unlabelled backbone traffic) -- unusable for a labelled recall/FPR evaluation without a separate, substantial labelling effort.

- **CIC-IDS2017** (https://www.unb.ca/cic/datasets/ids-2017.html): the PCAP directory redirects to a dataset request/index page rather than offering direct file downloads.

- **UNSW-NB15**: not attempted directly given the above; similarly hosted as large archives typically requiring a request process.


If you have access to one of these (or another labelled capture set) and want to substitute it in, the integration point is `ml_engine.evaluate.build_eval_set()` -- replace it with a loader that reads real packets through `core.sniffer.read_pcap` and labels windows from the dataset's ground truth, then run the extractor over them exactly as `ml_engine.traffic_profiles.build_feature_dataset` does.

## Iteration history

Kept here (regenerated each run, not overwritten) because the numbers above alone don't explain *why* the model looks the way it does. Two methodology bugs were found and fixed by looking at *why* validation FPR was catastrophic for specific normal scenarios, not just tuning the model harder against the same broken features/data:

1. **`dest_port_entropy` was normalized by `log2(unique_port_count)`.** This bounded it to [0, 1], but conflated "evenly split across 2 values" with "evenly split across 50 values" -- both normalized to ~1.0. Real web traffic realistically only ever uses 1-2 destination ports (80/443) no matter how many sites are visited, so it scored nearly as "scan-like" as an actual port scan. Fixed by using raw (unnormalized) Shannon entropy in bits, so 2 ports caps at 1 bit while a 50-port scan reaches ~5.6 bits -- a real numeric gap the model can use. See core/extractor.py's `_shannon_entropy` docstring.

2. **`profile_mixed_office` let each sub-traffic-type (web browsing, DNS, bulk transfer) pick its own random source IP.** A single simulated workstation doing three things at once ended up looking like 2-3 different hosts, inflating `unique_source_ip_count` in a way that doesn't happen on a real single-host workstation. Fixed by generating one source IP per mixed_office window and threading it through every sub-profile call. See `ml_engine/traffic_profiles.py`'s `profile_mixed_office` docstring.

Before these two fixes, the same OneClassSVM/LocalOutlierFactor search produced an aggregate FPR that looked acceptable (~0.16-0.17) while `web_browsing` and `mixed_office` individually sat at 40-68% FPR -- exactly the failure mode `tests/test_ml_quality.py`'s per-scenario gate exists to catch. Fixing the underlying feature/data bugs (not the decision threshold) resolved it: aggregate FPR dropped to ~0.02 and every individual scenario is comfortably under the 10% per-scenario budget.

One known cosmetic quirk, not a correctness issue: `LocalOutlierFactor`'s decision_function isn't bounded the way `IsolationForest`'s is, so anomaly scores for extreme windows (e.g. an ICMP flood) can be very large in magnitude (see the per-scenario table above). `ui/console.py` formats the displayed score with `.4g` rather than a fixed decimal count specifically to keep this readable; the NORMAL/ANOMALY classification itself is unaffected.
